# Размещение на хостинге

## GitHub Pages для демонстрации

Основные исходники находятся в `astro-js-production`, опубликованные статические файлы — в `main`. Исторический React-эталон остаётся в `source`; экспериментальная ветка `design/3d-motion-lab` не участвует в этой публикации.

`npm run build:pages` использует отдельный `astro.pages.config.mjs` с базовым путём `/39donuts-franchise-concept-demo/` и создаёт `dist-pages/`. Проверка подтверждает префиксы ресурсов и ссылок, наличие готового HTML, отсутствие 3D и режим `noindex`. Canonical продолжает указывать на официальный домен. Готовая папка содержит `.nojekyll`; правила Apache в неё не включаются.

Для публикации заменяется содержимое `main` файлами `dist-pages/`, затем проверяется завершение Pages deployment и работа живого адреса. Сохраняется история коммитов, исходная ветка `source` не удаляется. Не нужно копировать сборку для корня официального домена в подпапку GitHub Pages.

Далее описан отдельный официальный выпуск для корня `https://39donuts.ru/`. Публикация демонстрации на GitHub Pages не меняет официальный сайт компании и не подключает Telegram.

Astro выпускает статические HTML, CSS, JavaScript и ресурсы. Для обслуживания этих файлов хостингу не нужны Node.js, Astro, React или сборочные зависимости. Серверная отправка заявок подключается отдельно к существующему обработчику компании.

## 1. Подготовить выпуск

В каталоге проекта:

```sh
nvm use
npm ci
npm run release
```

Команда проверяет форматирование, код и готовую production-сборку, затем создаёт:

- `dist/` — файлы для загрузки;
- `releases/39donuts-production.tar.gz` — архив содержимого `dist/`, включая скрытый `.htaccess`;
- `releases/39donuts-production.tar.gz.sha256` — контрольную сумму архива.

Для упаковки нужна утилита `tar`. Если архивация недоступна, `npm run check` всё равно создаёт и проверяет `dist/`, который можно загрузить напрямую. Не загружайте исходники проекта, `node_modules/`, `.env`, `dist-preview/` или папку `releases/` в публичный каталог.

Настройки по умолчанию рассчитаны на корень `https://39donuts.ru/`. Вариант с другим доменом описан в [SEO.md](SEO.md); размещение в подпапке этой конфигурацией не предусмотрено.

## 2. Сохранить существующий сайт и серверную часть

Перед заменой сохраните копию текущего сайта и настроек хостинга. Уточните фактический корневой каталог домена в панели хостинга: его имя зависит от провайдера.

Загружайте **содержимое** `dist/` в этот каталог, без дополнительной папки `dist`. Существующие `/api/`, серверные секреты, сертификаты и системные файлы компании нужно сохранить. Если там уже есть `.htaccess`, сначала сохраните его копию и объедините правила: слепая замена может убрать настройки PHP, API или HTTPS. Не используйте синхронизацию с удалением всех отсутствующих в сборке файлов: статическая сборка не содержит действующий обработчик заявок.

После подключения обработчика требуется проверить, что заполненная анкета действительно поступает в Telegram. До получения исходников компании анкета выполняет только локальное завершение и не отправляет данные. Успешная SEO-сборка не подтверждает работу отправки.

## 3. Применить правила веб-сервера

### Apache

В `dist/` включён скрытый `.htaccess`. Он задаёт главную страницу, страницу ошибки 404, а при доступных модулях — 301-редиректы, заголовки и сжатие.

Провайдер должен разрешать используемые директивы `.htaccess`; для редиректов нужен `mod_rewrite`. Если сервер игнорирует этот файл или запрещает его директивы, эквивалентные настройки применяются в панели хостинга либо конфигурации виртуального хоста. После загрузки проверьте, что сайт отвечает без ошибок 500, а отсутствующий URL возвращает 404.

Правила приводят HTTP и www к HTTPS без www, `/index.html` к `/`, а старые `/e`, `/f`, `/g` к главной. Если HTTPS завершает внешний прокси, хостинг должен корректно передавать признак HTTPS: иначе правило перенаправления может зациклиться. Действующие правила `.htaccess` нужно согласовать с новыми, сохранив обработчик `/api/`.

### Nginx

Пример `deploy/nginx-location.conf.example` включается **в существующий HTTPS server-блок** для `39donuts.ru`. Это набор правил для сайта, а не полный файл сервера. Сохраните действующие `root`, TLS-сертификаты и маршрутизацию PHP/backend для `/api/`.

Если `location /` или `error_page` уже заданы, объедините правила с существующей конфигурацией, не создавая дубликаты. Для HTTP и HTTPS www нужны серверные 301-переходы на `https://39donuts.ru$request_uri`, как указано в комментариях примера. Перед перезагрузкой проверьте конфигурацию командой `nginx -t`.

Основной маршрут использует `try_files $uri $uri/ =404`. Не используйте возврат `/index.html` для любого неизвестного пути: он выдаёт главную вместо настоящей ошибки 404. Файлы в `/_astro/` имеют имена с хешем и могут кешироваться надолго.

### Другой статический хостинг

Настройте в его панели те же canonical-редиректы и отдачу `404.html` с HTTP-кодом 404. Само наличие файла 404 или HTML-перехода со старой страницы не заменяет серверные коды ответов. Настройки зависят от провайдера; локальный предпросмотр не проверяет их на реальном домене.

## 4. Проверить после загрузки

| URL / проверка                                                               | Ожидаемый результат                                               |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `https://39donuts.ru/`                                                       | HTTP 200, текущая главная, canonical на этот URL, `index, follow` |
| `https://39donuts.ru/privacy-policy/`                                        | HTTP 200, политика, свой canonical                                |
| `https://39donuts.ru/robots.txt`                                             | HTTP 200, разрешено чтение и указан production-sitemap            |
| `https://39donuts.ru/sitemap.xml`                                            | HTTP 200, XML с главной и политикой                               |
| `https://39donuts.ru/og/39donuts-franchise.png`                              | HTTP 200, картинка для ссылок                                     |
| `http://39donuts.ru/`, `http://www.39donuts.ru/`, `https://www.39donuts.ru/` | 301 на HTTPS без www, без цикла                                   |
| `/index.html`, `/e`, `/f`, `/g`                                              | 301 на `/`, параметры запроса сохраняются                         |
| `/privacy-policy`                                                            | Переход на `/privacy-policy/`                                     |
| Несуществующий путь, например `/missing-page-check/`                         | HTTP 404 с оформленной страницей ошибки, без canonical            |
| Старые якоря, например `/#about`                                             | Открывается соответствующий блок главной                          |
| Заполнение анкеты                                                            | После подключения API заявка приходит в Telegram один раз         |

Проверьте также HTTPS-сертификат, изображения и шрифты, мобильное меню, форматы, FAQ и анкету на телефоне и компьютере. Убедитесь, что в официальном каталоге находится production-сборка: `dist-preview/` содержит `noindex` и не предназначен для индексации.

Для проверки ответов можно использовать `curl`:

```sh
curl -I https://39donuts.ru/
curl -I http://39donuts.ru/
curl -I https://www.39donuts.ru/
curl -I https://39donuts.ru/missing-page-check/
curl https://39donuts.ru/robots.txt
curl https://39donuts.ru/sitemap.xml
```

На этапе локальной подготовки реальные настройки DNS, TLS, серверные редиректы и права аккаунтов поисковиков не применяются. Их успешность подтверждается указанными проверками на официальном домене.

## 5. Зарегистрировать актуальную карту сайта

После проверки официального домена подтвердите сайт в Google Search Console и Яндекс Вебмастере, передайте `https://39donuts.ru/sitemap.xml` и выполните проверку URL главной и политики. Нужны доступ владельца и выданные сервисами данные подтверждения; в текущем выпуске нет выдуманных идентификаторов аккаунтов.

## Последующие изменения

Места редактирования исходников перечислены в [EDITING.md](EDITING.md). После правок выполните `npm run format`, затем `npm run release` и загрузите новый результат сборки. HTML и ресурсы должны относиться к одному выпуску: сначала загрузите новые ресурсы, затем страницы. При ошибке верните сохранённую копию статических файлов и конфигурации, сохраняя действующую серверную часть заявок.
